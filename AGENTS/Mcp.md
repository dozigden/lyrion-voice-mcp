# MCP Guidance

Read this before changing MCP registration, tool schemas, results, or error handling.

## Implemented transport

- Use the official C# SDK package `ModelContextProtocol.AspNetCore` 2.1.x.
- Serve stateless Streamable HTTP at `/mcp`.
- Do not enable legacy SSE, sessions, OAuth, or application authentication without a new architectural decision.
- MCP transport registration belongs in Api; public input/output records belong in Contracts.

## Current public tools

The implemented surface currently contains:

1. `search`
2. `browse`
3. `get_player_status`
4. `control_player`
5. `get_queue`
6. `manage_queue`
7. `play`

The first three-tool delivery slice was not a permanent limit. Add cohesive user-facing tools when their contracts and application boundaries are understood. Do not expose health, diagnostics, raw LMS commands, experimental search, or provider administration as MCP tools.

## Tool behaviour

- Keep tool handlers thin and use application services.
- Advertise concise server instructions during MCP initialisation for relationships that span tools: player discovery, search versus browse, opaque-reference routing, play versus queue-management semantics, and genuine ambiguity. Do not duplicate complete tool descriptions there.
- Treat [MCP_CONTRACT.md](../MCP_CONTRACT.md) as the working public contract until implemented schemas replace it.
- Return structured, agent-friendly results and opaque result references.
- Structured tool results must validate against their advertised output schemas. Emit required nullable properties explicitly as JSON `null`; do not omit them through serializer defaults.
- Propagate cancellation and map expected validation/upstream failures to useful tool errors without leaking stack traces.
- A search result reference carries both candidate correlation and underlying LMS identity. Expose it as `browseRef`, `playRef`, or both according to the result's capabilities; these may contain the same opaque handle and require no separate public `searchId`.
- Result and browse references are server-issued handles backed by one singleton in-memory registry shared by both codecs. Prefix each handle with a concise lowercase entity or browse-location label followed by 16 lowercase hexadecimal characters, such as `artist_`, `album_`, `track_`, `playlist_`, `genre_`, `year_`, `albums_`, or `tracks_`. The label is incidental operator guidance only: callers must treat the complete reference as opaque, pass it back unchanged, and never parse or construct it. Never return encoded application data in the handle.
- Handles expire absolutely 24 hours after issue, are all invalidated by application restart, and share a 10,000-entry bound. Remove expired entries first and evict the oldest issued handle when capacity is reached. Resolution is exact and case-sensitive; never guess, repair, decode, or fall back when a handle is unknown, altered, expired, or evicted.
- A handle is a short-lived hand-off value even though its maximum lifetime is 24 hours. Do not add a format version or LMS server identity, persist the registry, or promise that a handle survives restart or capacity pressure.
- `browse` takes one optional opaque `browseRef`. Omit it for the fixed local-library roots: album artists, artists, albums, genres, playlists, ratings, recently added, and years. Do not expose tracks at the root.
- Browse pages use a fixed internal size of 50. Return an opaque nullable `nextBrowseRef` rather than caller-controlled offset, limit, filtering, or sorting.
- Browse items contain kind, title, optional artist and album, whichever of `browseRef` and `playRef` apply, and an optional numeric rating used only for tracks returned through rating browse. Omit an unavailable capability reference rather than returning a universal reference plus boolean flags.
- Album artists and ordinary artists are navigation only. Never attach playable media to their browse handles, and reject artist identities in playable-reference resolution even if an internal or stale handle contains one.
- Album artists and artists browse to albums; albums browse to tracks; genres and years browse to albums; playlists browse to tracks. Ratings browse to integer buckets 0–5, then to catalogue tracks whose public decimal rating floors to that bucket. Recently added returns LMS `sort:new` albums. The first pass is the local library only and excludes plugins, provider browsing, virtual-library selection, and player context.
- Pure browse references have no search correlation. When browsing starts from an artist, album, or playlist search reference, propagate that real candidate correlation through every descendant and continuation. A later successful `play` or queue addition marks the originating search candidate selected; browsing alone does not. Never create a synthetic correlation for a root browse flow.
- `get_player_status` returns every discovered player with full voice-relevant power, mode, volume, optional mute, and now-playing state. It deliberately excludes queue, connectivity, and grouping information.
- `control_player`, `get_queue`, `manage_queue`, and `play` accept either a raw LMS player ID or an exact unique player name currently returned by `get_player_status`; do not wrap either in an application reference. Resolve IDs first, then names case-insensitively after trimming. Reject unknown and duplicate names with actionable tool errors; never fuzzy-match, remember historical names, or invent aliases. Successful responses continue to return the canonical raw player ID.
- `control_player` accepts exactly one lowercase action: `resume`, `pause`, `stop`, `next`, `previous`, `power_on`, or `power_off`. It excludes volume, mute, seek, grouping, and queue operations and returns the selected player's refreshed full status.
- Register `PlayerControlTools` through `PlayerControlToolRegistration` so malformed enum values become corrective tool errors while the generated schema retains the agreed lowercase action enum.
- `get_queue` takes one player and returns its complete queue up to the LMS 300-item limit. Return only the player ID, nullable current LMS index, and ordered items with LMS index plus title, optional artist, album, and duration. Do not expose pagination, queue revisions, search-result references, or LMS media IDs.
- `manage_queue` takes one player, `clear`, `append`, or `insert_next`, and optional `playRef` values from search or browse. `clear` accepts no items. Additions require at least one item, inspect the complete batch before mutation, skip invalid, unavailable, or over-capacity items, and preserve the relative order of items that fit within the 300-item limit. They return requested and completed reference counts, indexed skipped-item reasons, the canonical player ID, and a nullable refreshed queue length plus refresh error. Append and insert-next must not change power or playback state; clear empties the queue and stops playback through LMS's native clear behaviour.
- Register `QueueManagementTools` through `QueueManagementToolRegistration` so malformed enum values become corrective tool errors while the generated schema retains the agreed lowercase action enum.
- `play` accepts a non-empty ordered `playRef` list, inspects the complete batch before mutation, skips invalid or unavailable items, loads the first usable item, and appends later usable items in relative order. It replaces the queue, powers on when required, starts playback, and returns requested and completed reference counts, indexed skipped-item reasons, and nullable refreshed player status plus refresh error. Append and play-next behaviour belong to `manage_queue`; do not add a placement mode to `play`, and tell callers not to append the same items immediately before calling `play`.
- Stable skipped-item reason names are `invalid_reference`, `media_unavailable`, `queue_capacity`, `lms_error`, and `not_attempted`. A batch with no usable item is a plain tool error because LMS was not changed. A mutation attempt with no confirmed completion is a structured tool error containing zero completed items and refreshed observable state, because LMS may still have changed before its failure became visible. Once one item completes, later LMS mutation failure produces structured partial success, stops the batch, and marks only confirmed items selected. Never retry a whole partial or uncertain batch automatically.
- Register `PlaybackTools` normally through the SDK; it no longer requires an enum-binding workaround.
- Model expected search, browse, player-control, queue-management, and playback validation or business rejection as application outcomes, not exceptions. Tools map rejections to `CallToolResult` with `IsError = true`; keep `OutputSchemaType` set to their successful response contracts.
- Search uses the production catalogue resolver for artists, albums, and tracks, followed by isolated LMS playlist discovery. Return separate `artists`, `albums`, `topTracks`, `tracks`, and `playlists` lists rather than a flat mixed list. Current internal caps are 5, 5, 5, 30, and 5 respectively; do not expose caller-selected limits or search pagination. `topTracks` contains relevant tracks rated 4 or above. `tracks` remains eligible to draw from that same high-rated population, but remove the particular `topTracks` occurrences from it before returning the response.
- Search may vary equal-relevance track results and spread them across albums. Within an equal-relevance top-track band, higher ratings improve selection odds without strictly ordering ratings or excluding eligible four-star tracks. A unique exact whole-query artist result expands through canonical artist-to-track relationships and populates the required nullable `exactArtistMatch` object with `name` and `discographyBrowseRef`; `artists` must then be empty. On an unconstrained exact search, `albums` is a varied preview of up to five albums from the complete album-artist relationship; guest-appearance-only albums are excluded and ordinary album search is unchanged. The discography reference browses the complete album-artist discography. Duplicate exact artists, fuzzy matches, or an exact album or track—including a self-titled album conflict—keep `exactArtistMatch` null and retain ordinary search behaviour. Rating-constrained exact artist searches use the same representation but return qualifying tracks only. This is automatic search behaviour, not another public input or tool.
- Unresolved artist search results contain only `name` and `browseRef`. Albums and playlists contain `browseRef` and `playRef`; tracks contain `playRef`. Include concise response guidance explaining the exact-artist distinction and that passing a browse reference to `browse` opens that location and returned `browseRef` values continue through the tree.
- Every track search result has a decimal-number `rating` from 0 to 5, obtained by dividing the required native LMS value by 20. Zero means the track has no positive LMS rating; do not add a separate public unrated state. Omit `rating` from artist, album, and playlist results, and never expose the native 0–100 value through MCP.
- `search` takes required media-name text in `name` and accepts optional `rating` and `ratingMatch` arguments only as a pair. Rating is a decimal number from 0 to 5 and `ratingMatch` is `exact` or `at_least`. Describe `exact` as exactly the supplied rating and `at_least` as that rating or higher, including the example that rating 4 with `at_least` means 4+. Tell callers to keep ratings out of `name`; a constrained search returns tracks only and does not call playlist search. Register search through `SearchToolRegistration` so the SDK-generated schema retains the numeric bounds and stable match enum.
- Search names are limited to 500 characters and 20 normalised letter-or-digit tokens and must contain at least one such token. Reject oversized, wildcard-only, and recognisable numeric rating syntax as an expected application outcome before either retrieval source runs. The rating-syntax correction must direct callers to the separate `rating` and `ratingMatch` fields without broadly rejecting ordinary numbered media names. Direct rating-only exploration to the Ratings browse tree; `*` is not a wildcard.
- Register durable tool-call observation once through the SDK call-tool filter so current and future tools are covered. Record the complete ordered arguments and complete returned `CallToolResult`, subject to the explicit configured JSON bound; distinguish success, returned tool error, cancellation, unexpected failure, and startup interruption. Observation failure must never change a successful tool outcome.
- The SDK surfaces missing or unbindable reflected-tool parameters as `ArgumentException` with `arguments` as the parameter name inside the filter. Convert that binding case to a returned and recorded tool error; do not enter it in the application error log. Other thrown tool exceptions remain unexpected failures and must link to an error-log row.
- Tool calls and their unexpected-error links are exposed only through the REST administration UI. Never add diagnostic history as an MCP tool.
